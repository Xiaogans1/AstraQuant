# AstraQuant 开源项目比较

评估日期：2026-07-27

## 评估方法

项目不会仅按 Star 排序。评估维度包括：

1. 维护活跃度与版本节奏。
2. 架构边界和扩展能力。
3. 测试、CI、文档和工程质量。
4. 研究、回测、执行、数据或 UI 的专项成熟度。
5. 对中国 A 股与国内期货的直接或间接价值。
6. 许可证对未来分发和商业化的影响。

## 1. vn.py

### 值得借鉴

- `EventEngine` 使用类型化事件分发行情、订单、成交、持仓和账户更新。
- `MainEngine` 组合 Gateway、功能引擎和应用，国内接口生态成熟。
- `BaseGateway` 为行情订阅、下单、撤单、历史查询提供统一边界。
- OMS 对订单、成交、持仓、账户和合约做集中状态维护。
- 对国内期货开平、交易接口和实际运行环境的经验价值很高。

### 不应照搬

- 当前事件引擎偏轻量，AstraQuant 需要补充事件版本、持久化、幂等和重放能力。
- Qt UI 不适合作为现代主题化桌面界面的基础。
- 核心对象不应直接泄漏到 AstraQuant 所有上层模块，否则未来更换执行实现困难。

### AstraQuant 决策

将 vn.py 视为首要国内交易生态入口，通过独立适配器映射到 AstraQuant 自有领域模型。优先复用成熟 Gateway，不复制整套 UI 和全局引擎结构。

## 2. Qlib

### 值得借鉴

- 数据、Dataset、Model、Strategy、Recorder 和 Workflow 的研究管线较完整。
- 实验记录和可重复研究意识强，适合因子与机器学习工作流。
- 对中国股票研究已有大量示例和社区经验。
- 数据处理器、缓存和训练/验证/测试切分方式值得参考。

### 不应照搬

- Qlib 的主要优势是研究，不是国内实时交易执行。
- 官方或社区数据不能直接视为生产级数据源，数据版本和质量仍需 AstraQuant 自己治理。
- 不应要求所有普通策略都进入 Qlib 的模型和数据格式。

### AstraQuant 决策

Qlib 作为可选研究后端，通过 `ResearchProvider` 和标准信号数据结构接入。AstraQuant 的数据目录、策略元数据和交易核心不依赖 Qlib。

## 3. QuantConnect LEAN

### 值得借鉴

- 证券、交易所、订单、组合、经纪商和数据订阅的领域模型非常完整。
- 回测与实盘共享算法生命周期，降低两套系统语义漂移。
- Handler 和接口边界覆盖数据源、交易、结果、实时任务和历史数据。
- 大规模回归测试体现了交易引擎对确定性和兼容性的重视。

### 不应照搬

- 仓库规模很大，C# 技术栈和全球市场假设会显著增加第一版复杂度。
- 将 LEAN 直接嵌入 Python/Tauri 桌面产品会引入跨运行时和部署负担。
- 国内交易规则需要单独建模，不能只做符号或市场名称映射。

### AstraQuant 决策

学习其领域模型、算法生命周期和回归测试方法；第一阶段不嵌入 LEAN 引擎。

## 4. NautilusTrader

### 值得借鉴

- Rust 核心与 Python 控制面分离，兼顾性能、安全和策略开发效率。
- 研究、确定性仿真与实盘使用统一的事件驱动语义。
- 模块边界清晰，覆盖 model、data、execution、risk、portfolio、persistence 和 adapters。
- 订单状态机、事件溯源、消息总线和高精度时间模型非常适合生产交易系统参考。
- 测试夹具和适配器契约的覆盖方式值得学习。

### 不应照搬

- Rust/Python 双栈对第一版团队规模而言成本过高。
- 国内 CTP 与 A 股通道仍需独立工作。
- LGPL-3.0 需要谨慎评估修改、链接和分发义务。

### AstraQuant 决策

重点借鉴事件信封、确定性时钟、订单状态机、风险管线和事件溯源。第一阶段用 Python 实现清晰接口，只有性能数据证明必要时才下沉 Rust。

## 5. OpenBB

### 值得借鉴

- Provider、Fetcher、标准查询参数和标准数据模型形成了成熟的数据插件体系。
- 同一数据能力可供 Python、REST API 和不同消费端使用。
- 仓库包含 Tauri 桌面端，验证了现代 Web UI 与本地桌面壳的组合。
- 产品工作区、扩展和金融数据发现体验具有很高参考价值。

### 不应照搬

- 仓库整体使用 AGPL-3.0，直接复制或形成衍生作品会影响 AstraQuant 的许可证选择。
- OpenBB 的重点是数据与分析工作区，不是国内交易执行和风控。
- 大量全球数据 Provider 不应成为第一版负担。

### AstraQuant 决策

借鉴产品体验和 Provider 概念，但自主设计接口与实现；不复制其核心代码。

## 综合判断

AstraQuant 不应选择一个项目 Fork 后大改。推荐组合为：

```text
产品工作区思路：OpenBB
研究工作流：Qlib
交易领域模型：LEAN
事件与执行架构：NautilusTrader
国内实盘生态：vn.py
```

最终系统保留自己的领域模型、数据契约和进程边界。外部项目通过适配器或可选 Provider 接入，以控制技术、许可证和升级风险。
