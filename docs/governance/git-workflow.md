# GitHub 与多端协作规范

## 目标

GitHub 是 AstraQuant 源代码、设计和协作事实来源，不是用户市场数据或运行状态的同步盘。

远程仓库：`https://github.com/Xiaogans1/AstraQuant`

## 必须提交

- 源代码与自动化测试。
- README、架构、研究记录和决策文档。
- API、事件和数据结构定义。
- SQLite 迁移和数据目录 Schema。
- 示例配置与 `.env.example`。
- UI 主题令牌和拥有合法来源的公共素材。
- 包管理器锁文件。
- CI、格式化、Lint、测试和打包配置。
- 小型、脱敏、许可证明确的测试数据夹具。

## 禁止提交

- `.env`、令牌、密码、数据源密钥，以及任何误加入的真实交易凭据。
- 行情、财务、Tick、K 线、因子和用户导入数据。
- SQLite、DuckDB、Parquet、日志和本地缓存。
- 回测报告、模型权重和大规模生成产物。
- 用户自定义背景、私人主题和个人工作区状态。
- 上游项目克隆、副本或来源不明代码。
- 未确认分发权的数据集、字体、图标和动漫素材。

## 分支模型

- `main`：始终保持可构建或仅含已确认设计。
- `feature/<topic>`：功能开发。
- `fix/<topic>`：缺陷修复。
- `docs/<topic>`：独立文档工作。
- `release/<version>`：需要稳定期时使用。

第一批设计文档用于建立空仓库，可以直接推送 `main`。进入代码实现后，默认通过短生命周期分支和 Pull Request 合并。

## 自动提交和推送规则

Codex 或自动化工具可以在以下条件全部满足时自动提交：

1. 当前改动范围与用户批准的任务一致。
2. 已检查 `git diff`，不存在无关用户改动。
3. 相关格式化、测试、构建或文档检查通过。
4. 秘密扫描未发现凭据。
5. 第三方代码和素材已有来源与许可证记录。
6. 提交是一个可以解释和回滚的逻辑单元。

自动推送策略：

- 纯文档和仓库初始化：验证后可推送当前批准分支。
- 功能代码：推送功能分支，优先创建 Draft PR。
- 风险规则、实时信号、凭据和数据迁移：必须通过 PR 检查，不自动直接合并 `main`。
- 测试失败或状态不确定：允许本地保留改动，不得以“临时可用”为由推送。

建议提交信息使用简洁的简体中文，例如：

```text
docs: 完成产品设计与开源项目研究
feat(data): 增加本地数据目录
fix(risk): 修正日亏损阈值计算
```

## 多设备工作流程

每台设备只从 Git 获取代码和公共配置：

1. 克隆仓库。
2. 从 `.env.example` 创建本地配置。
3. 初始化本地数据目录和凭据。
4. 运行依赖安装、迁移和自检。
5. 开发前同步远程分支，使用独立功能分支。
6. 数据通过用户选择的本地磁盘、NAS 或私有同步方案管理，不进入 Git。

未来若需要多设备共享策略运行结果，应设计显式的私有同步或只读监控协议，而不是提交数据库文件。

## 版本与发布

- 使用语义化版本。
- Release 只包含可分发程序、校验值、变更说明和第三方声明。
- 构建产物由 CI 生成，不直接提交仓库。
- 数据 Schema 和事件 Schema 必须有版本及迁移策略。
- 正式发布前生成软件物料清单和 `THIRD_PARTY_NOTICES.md`。
