# AstraQuant 正式数据工作台重构设计

## 1. 背景与问题

“数据与连接”仍展示 Phase 2 的 `fixture` 合成样例、固定证券、固定日期和“导入示例
数据”。这些控件曾用于验证本地快照闭环，但已经与 Phase 3A 的东财真实行情主路径冲突，
容易让用户误以为正式产品需要手工导入样例。

本次同时修复连接面板出现 `Failed to fetch` 的问题。排查证据表明：运行中的桌面应用在
16:43 启动，之后前端通过 Vite 热更新取得了新增市场 API；Python 本地服务没有热重启，
仍使用不允许 `PUT` 的旧 CORS 配置。对运行端点发送配置预检得到
`Disallowed CORS method`，而当前源码已经允许 `PUT`。因此失败发生在 Token 校验之前，
并不证明用户 Token 错误。

## 2. 目标与边界

本次交付一个诚实、可长期保留的正式数据工作台：

- 顶部继续使用东财 SDK 连接面板；
- 页面只展示真实 Provider 产生的数据集；
- `fixture` 数据继续保留在底层和自动化测试中，但不进入正式用户界面；
- 删除样例选择、固定日期、复权选择和“导入示例数据”；
- 保留不可变快照、质量报告和行情预览；
- 历史自动同步尚未实现时明确说明，不提供虚假按钮；
- 不删除用户磁盘上的既有快照，不修改真实数据；
- 不实现真实交易、自动下单或本轮之外的历史同步后端。

## 3. 方案比较

### 方案 A：只改文案

保留现有表单，把“样例”改成“历史数据”。改动最小，但控件仍调用 `fixture`，属于界面
伪装，不能采用。

### 方案 B：同时完成东财历史同步

把 SDK 历史接口、Worker、落盘、进度和 UI 一次完成。闭环最好，但这是独立的数据工程
阶段，会把本次前端清理扩大为高风险后端项目。

### 方案 C：正式工作台先行（采用）

立即移除开发入口，保留真实仓库与质量能力；历史同步区域只陈述当前能力边界。下一阶段
再用单独计划接入东财历史同步。该方案最快消除误导，同时不牺牲已经验证的数据基础设施。

## 4. 信息架构

```text
数据与连接
├─ 东财实时行情连接（已实现、可操作）
├─ 本地数据边界
│  ├─ 实时行情：只读观察
│  ├─ 历史同步：尚未接入
│  └─ 本地仓库：真实快照数量
└─ 数据工作台
   ├─ 本地行情仓库：只列真实 Provider 数据集
   └─ 快照质量：覆盖区间、来源、行数、问题和最近行情
```

页面的视觉签名是“数据管线轨道”：连接、同步、快照和特征四个节点只根据真实能力点亮。
其余布局保持 Astra Minimal 的细线、冷白、青色状态语义和清晰数据字体，不新增装饰性
图表或无意义动画。

## 5. 数据契约

`DatasetSummary` 增加最新快照的只读元数据：

- `latest_provider_id`
- `latest_row_count`
- `latest_min_event_time`
- `latest_max_event_time`

API 从目录中的 `latest_snapshot_id` 查询已发布快照并填充字段。前端只展示
`latest_provider_id !== "fixture"` 的数据集；缺失 Provider 的旧记录同样不冒充真实数据。

## 6. 页面状态

- 无真实数据：显示“尚无真实历史数据”，解释实时行情目前只用于观察，历史同步接入后才
  会生成本地仓库快照。
- 有真实数据：展示真实数据集列表和最新快照详情。
- 本地服务离线：保留已缓存真实目录，显示离线横幅，不提供导入动作。
- 质量拒绝：保留错误与警告文本，禁止作为特征输入。
- `fixture`：不显示、不计数、不参与页面指标。

## 7. 连接错误处理

连接面板把网络错误翻译为可行动信息：本地服务不可达时提示“本地行情服务版本已变化，
请重启 AstraQuant 后重试”，而不是裸露 `Failed to fetch`。开发文档明确 Python 后端源码
变更后需要重启桌面进程；正常用户每次启动都会获得同一版本的前后端。

## 8. 验收标准

1. 正式页面不存在“导入本地样例”“导入示例数据”或 `fixture`。
2. 已存在的合成快照不会出现在数据集列表和统计中。
3. 六大核心行情与东财连接功能不受影响。
4. 真实数据集仍可查看质量报告和行情预览。
5. 网络/CORS 失败不再原样显示 `Failed to fetch`。
6. 前端、Python、仓库策略和 CI 全部通过。
